     DATA-01 · Exam data loader and read APIs

     Context

     Both UI screens (Screen 1: list of 4 students, Screen 2: one student's 8
     questions) need real data to render. Right now the app has no lib/ folder
     and no API routes — just the default Next.js scaffold. This ticket builds
     the loader that reads data/exam_data.json and the two read-only API routes
     the frontend will call. No grading, no marks, no AI (that's later tickets).
     This also lays down invariant I4: the "no submission" marker must be set
     here, before any grading exists, so a skipped question can never
     accidentally reach the AI later.

     Files to add

     - lib/exam/loadExam.ts — pure-ish loader/builder functions (no I/O beyond
       reading the already-imported JSON)
     - app/api/submissions/route.ts — GET: list of 4 students
     - app/api/submissions/[name]/route.ts — GET: one student's full 8-question
       grid, or 404
     - lib/validation/schemas.ts — zod schemas for the exam JSON shape
       (validated once at load, per CLAUDE.md §4.2 rule 3: validate at every
       boundary — the JSON file is a boundary too)
     - tests/loadExam.test.ts — unit tests for the loader functions (thin per
       ticket, but these are domain-ish pure functions so test them directly per
       CLAUDE.md §7)
     - tests/api-submissions.test.ts — thin tests hitting the two route handlers
       directly

     Design, matching technical-spec.md §7

     data/exam_data.json has questions (8, fixed) and student_responses (sparse,
     keyed by student+question_id). The loader must:
     1. Load and zod-validate the raw JSON once (module-level, so route handlers
        just import the already-validated data — avoids re-parsing per
        request).
     2. Derive the fixed list of 4 student names from the distinct student
        values in student_responses (Aisha, Ben, Chen, Diego) — not hardcoded,
        so the loader stays correct if the source data changes.
     3. getSubmissionsList() → { name: string }[], one entry per student (used
        by Screen 1 / the list API).
     4. getStudentSubmission(name: string) → builds the full 8-question grid
        from the question list, then attaches each student's response where it
        exists. A question with no matching response (or an empty-string
        response, per Aisha's blank Q7) gets status: "no_submission", response:
        null. This is the exact "build from question list first" decision in
        spec §7.3 — looping over responses alone would hide blanks/missing
        entries. Returns null if the student name isn't found, so the route can
        turn that into a 404.

     Note: Aisha's Q7 response is "" (empty string present in the data) vs
     Diego's Q2/Q6/etc which are simply absent from student_responses. Both must
     be treated as "no submission" — the loader checks for missing-or-blank,
     not just missing.

     Shape returned by the detail API (per spec §7.1/§7.2 + ticket)

     Each of the 8 questions becomes an object with: questionId, question,
     rubric, modelAnswer, maxMarks, response (string or null), status
     ("no_submission" | "pending" — only these two exist before grading starts;
     grading/graded come in later tickets but the type should allow for them now
     since GradingContext will reuse this shape).

     API routes

     - GET /api/submissions → 200 { students: [{ name }, ...] } (4 entries)
     - GET /api/submissions/[name] → 200 { name, questions: [...8 items...] },
       or 404 { error: "Student not found." } for an unknown name (per spec §15
       error table)

     Test plan (thin, per ticket's own table)

     - Happy: list API returns exactly 4 students
     - Happy: detail API for Diego → 8 questions, 6 no_submission, Q2 and Q6
       present with their response text
     - Happy: detail API for Aisha → Q7 is no_submission (covers the
       blank-string case, not just missing)
     - Failure: detail API for "Zzz" → 404 with a clear message, no crash

     Verification

     - npm test — paste real output for the new test files
     - npx tsc --noEmit
     - npm run lint
     - npm run build
     - Manually hit curl http://localhost:3000/api/submissions and
       /api/submissions/Diego and /api/submissions/Zzz against npm run dev to
       eyeball the real JSON shape
