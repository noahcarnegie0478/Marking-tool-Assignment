     UI-02 · Final UI polish, review badges, wrap

     Context

     UI-01 and GRADE-01 already built a fully working app (Screen 1 list, Screen
     2 question cards, real AI grading, needs_review). It currently uses plain
     default Tailwind styling (app/page.tsx, app/student/[name]/page.tsx) —
     functional but not "considered and clear," which is what UI-02 asks for.

     The user supplied a reference mockup, public/Maths Exam Marking Tool.html.
     It's a bundled Artifact export; I decompressed its embedded template and
     found the exact intended design: a cream/warm theme (#FFFAF3 base, #FFF2DB
     cards, #D11A33 red accent), Hanken Grotesk font, avatar-initial circles,
     status pills, a Q-number + needs-review/no-submission badge row,
     rubric/response layout, and a sticky bottom action bar with a striped
     progress bar while grading. This plan re-skins the two real screens to
     match that reference, using the real app's data and state, not the mockup's
     hardcoded demo data.

     Scope is presentation only (ticket says "Invariants touched: none"). No
     business logic, reducer shape, or API changes.

     Approach

     1. Theme + font — app/layout.tsx, app/globals.css
     - Swap Geist/Geist_Mono for Hanken_Grotesk via next/font/google (same
       pattern already used, no new dependency).
     - Replace the default Tailwind light/dark CSS vars in globals.css with the
       mockup's palette as CSS custom properties (cream base, card cream, deep
       red, warm text #2A2320, muted #9A8C7C, warning amber #8A6400/#FBECCB).
       Drop the prefers-color-scheme: dark block — the mockup has no dark mode
       and the ticket doesn't ask for one.
     - Fix the leftover default <title>/description in metadata (flagged, not
       fixed, in UI-01's review) to the real exam title.

     2. Small pure helper — lib/ui/studentAvatar.ts (new)
     - The mockup hardcodes one color per demo student. The real app has 4 names
       from data, not fixed IDs, so: a pure function studentAvatarColors(name):
       {bg, color} that picks from a small fixed palette (same hues as the
       mockup: red, tan, blue, green) via a stable hash of the name. Pure, no
       I/O — fits lib/ conventions (§5 of CLAUDE.md).

     3. Screen 1 — app/page.tsx
     - Header: eyebrow label + "Year 12 Mathematics" title (from real exam data
       context, not hardcoded demo copy).
     - Stat row: Submissions / Marked / Questions-each, computed from the real
       students list + results (marked count via existing getStatus).
     - Replace the <ul> with the mockup's card: header row (Student / Status /
       Score), then one row per student — avatar circle, name, "8 responses"
       meta, status pill (uses existing getStatus), score (uses existing
       getTotal), chevron.
     - Loading and error states get the same cream card treatment instead of
       bare <p> text, so they match the "no blank/crash" acceptance criterion.
     - Reuses getStatus/getTotal from lib/state/selectors.ts as-is — no selector
       changes.

     4. Screen 2 — app/student/[name]/page.tsx
     - Header: back link, avatar + name + "Year 12 Mathematics · Response
       Marking" subtitle, total on the right (color flips to red once marked,
       matching mockup).
     - Question cards per the mockup: Q{n} badge, ⚠ Needs review badge when
       question.needsReview, No submission badge when status ===
       "no_submission", question text, Rubric block, Response block, mark box
       (mark / maxMarks, muted dash before grading).
     - The "failed card" acceptance criterion: gradeStudent's existing safe
       fallback already sets needsReview: true with feedback: "Could not grade
       this response." on any API failure — this becomes visible automatically
       once the needs-review badge + feedback text are rendered, with no new
       state needed.
     - Sticky bottom bar: progress bar + "Grading N of total…" while
       gradingProgress is set (reusing the real done/total, striped-animation
       CSS from the mockup); Return + Grade/Re-grade with AI buttons otherwise.
     - notFound and loadError states get the same themed empty-state treatment
       as Screen 1, not bare text.

     5. Reflection doc — reflection.md (repo root, matching journal.md's
     existing convention — this repo has no docs/ folder despite the ticket
     text)
     - Half a page: what the tool does, why needs_review matters (the "don't
       blindly trust" story), and naming the parked per-question redo/adjust
       button as the next step — matching the ticket's "Out" scope note.

     6. Verify
     - npm run lint, npx tsc --noEmit, npm test, npm run build — paste real
       output per CLAUDE.md §9.
     - No browser tool available this session, so I cannot click through it
       myself; I'll say so explicitly and ask the human to do one manual pass
       (this matches how UI-01's entry handled the same gap).
     - Per CLAUDE.md §3, this still needs the blind-review step before being
       marked done — I'll note that in the end-of-ticket report, not mark it
       done myself.

     Files touched

     - app/layout.tsx — font swap, nothing else
     - app/globals.css — theme tokens
     - app/page.tsx — Screen 1 restyle
     - app/student/[name]/page.tsx — Screen 2 restyle
     - lib/ui/studentAvatar.ts — new, pure, small
     - reflection.md — new

     No changes to GradingContext.tsx, gradeStudent.ts, selectors.ts, API
     routes, or any human-owned doc.
